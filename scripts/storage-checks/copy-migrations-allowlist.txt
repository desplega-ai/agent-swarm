# check:copy-migrations allowlist (scripts/storage-checks/check-copy-migrations.ts).
# One row-changing statement of a Postgres migration per line: <migration>:<verb>:<table> -- <reason>.
# The reason says why db-copy does not lose the change. An entry that matches no statement fails the check.
#
# The starter dashboard is the one table where the two chains seed different rows (rows:metrics in
# schema-parity-allowlist.txt), so each statement that writes it is explained here.
367_baseline:insert:metrics -- the baseline seeds the starter dashboard with the SQLite queries of migration 092, the same row as the SQLite chain; the engine difference is the rewrite in 370
370_metrics_starter_postgres:update:metrics -- db-copy ports this rewrite itself: it matches each stock SQLite query of the copied dashboard against metric-query-ports.json and writes its Postgres form, which keeps operator edits (a rerun through after-copy.json would overwrite them); proof: packages/storage-postgres/test/data-copy.test.ts and the e2e scenario data-copy
374_schedule_next_run_at_utc:update:scheduled_tasks -- SQLite migration 374 normalizes nextRunAt before db-copy accepts the source at the matching migration head, so the copied rows already carry the UTC timestamps (src/tests/migration-schedule-next-run-at.test.ts).
