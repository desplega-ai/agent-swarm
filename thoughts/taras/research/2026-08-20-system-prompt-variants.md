# System prompt variants and task-handling prompts (as-is)

This document maps every prompt the swarm sends to a harness, and every branch that changes it.
Rendered text lives next to it in [`2026-08-20-prompt-variants/`](../../../work/prompt-variants/00-INDEX.md).
Regenerate with `bun scripts/dump-prompt-variants.ts` after you edit a template.

## 1. Two prompts per session

Every task session gets two inputs:

| Input | Built by | Delivered as |
|---|---|---|
| **System prompt** | `getBasePrompt()` in `src/prompts/base-prompt.ts`, then `+ requester profile + SYSTEM_PROMPT extra + cwd warning` in `runner.ts:6032` | claude: `--append-system-prompt-file`. codex: managed `AGENTS.md` in cwd. opencode: `.opencode/agents/swarm-<taskId>.md`. pi: `appendSystemPrompt`. claude-managed: static prefix text block of the first user message. devin: a cached playbook. |
| **Turn prompt** | `buildPromptForTrigger()` in `runner.ts:2825`, then `preamble + trigger + memories + cwd note` | the first user message |

The system prompt is **appended** to the harness's own system prompt. Claude Code's default prompt stays underneath ours.

The system prompt is rebuilt per task (`buildSystemPrompt()` at `runner.ts:4591`). Repo context, Slack context, and the skills list change between tasks. Identity files change only on profile refresh.

### 2.3 Inputs that drive the branches

| Input | Source |
|---|---|
| `role`, `agentId`, `swarmUrl` | runner config |

| `serverCapabilities` | `POST /api/agents` response `enabledCapabilities`. Undefined against older servers → legacy gating |
| `capabilities` | agent skill tags from config |
| `scriptsOnly` | swarm_config row > `SCRIPTS_ONLY_MCP` env |

| `repoContext` | `task.vcsRepo` → `/api/repos` config or convention fallback |
| `slackContext` | `task.slackChannelId` / `task.slackThreadTs` |
| `skillsSummary` | skills API, hot-reloaded per task |
| `mcpServersSummary` | installed MCP servers API |
| env: `SLACK_*`, `STEERING_ENABLED`, `AGENT_FS_API_URL`, `AGENT_FS_SHARED_ORG_ID` | worker container env |

### 2.4 Override layer

Every `eventType` can be overridden at runtime in the `prompt_templates` table (global → agent → repo scope chain, plus `skip_event`). Workers resolve through `POST /api/prompt-templates/render`; the API server resolves through `configureDbResolver`. The `header` field is never overridable. `{{@template[id]}}` refs expand up to depth 3 with cycle detection. Both fall back to code defaults when the DB/HTTP path fails.

The generated variants use **code defaults only**. Production may differ if someone edited templates in the UI.

## 3. Turn prompt (task handling)

### 3.1 Trigger → turn prompt

`buildPromptForTrigger()` maps the poll trigger to a template. `fmt` is the adapter's `formatCommand`: `/name` (claude, codex, opencode, claude-managed), `/skill:name` (pi), `@skills:name` (devin, but blanked because `hasMcp=false`).

| Trigger | Template | Rendered shape |
|---|---|---|
| `task_assigned` | `task.trigger.assigned` | `/work-on-task <id>` + `Task: "<desc>"` + `Requested by: name (email)` + attachment curl recipes + output instructions (generic store-progress, or the JSON `outputSchema` contract) |
| `task_offered` | `task.trigger.offered` | `/review-offered-task <id>` + desc + accept/reject sentence |
| `unread_mentions` | `task.trigger.unread_mentions` | 3 steps with `read-messages` / `send-task` |
| `pool_tasks_available` | `task.trigger.pool_available` | 3 steps with `get-tasks` / `task-action claim` |
| `channel_activity` | `task.trigger.channel_activity` | Slack message list + 3-step decision |
| paused task at boot | `task.resumption.with_progress` / `.no_progress` | `/work-on-task <id>` + RESUMED TASK banner + progress |
| `budget_refused` | none | handled in the poll loop with back-off |

Then the runner adds:

1. **Prepend** `## Prior Conversation Context` (`buildContextPreamble`, 4k-token budget, up to 5 ancestors) when `task.parentTaskId` is set. For `taskType=resume` it prepends `## Resuming Interrupted Task` instead (original description, last 50 tool-call lines, artifacts in flight, undelivered steering).
2. **Prepend** a `=== PERSISTED PROFILE SYNC REJECTION ===` banner when a profile file sync was rejected.
3. **Append** `### Relevant Past Knowledge` (`renderMemoriesPrompt`, top 5, similarity > 0.4, 300 chars each). Rating hint only when `MEMORY_RATERS` contains `explicit-self`.
4. **Append** `**Working Directory**: ...` when cwd differs from `process.cwd()`.

Sample renders: [`task-prompts.md`](../../../work/prompt-variants/task-prompts.md).

### 3.2 The commands the turn prompt invokes

The turn prompt is mostly a slash command. The real instructions live in `plugin/commands/*.md` (baked into the image, also seeded as skills):

| Command | Role in the flow |
|---|---|
| `work-on-task` | get-task-details → memory-search → pick research/plan/direct → store-progress milestones → complete → reply DONE. Escalate via `/swarm-chat` |
| `review-offered-task` | get-task-details → accept (`task-action accept` then `/work-on-task`) or reject with reason |
| `implement-issue`, `review-pr`, `respond-github`, `close-issue`, `create-pr`, `investigate-sentry-issue` | suggested by the GitHub/GitLab event templates |
| `swarm-chat`, `todos`, `user-management`, `start-leader`, `start-worker` | support |

### 3.3 Where task descriptions come from (the "generic / slack / gh" shapes)

The task **description** is the third prompt layer. It is written by whoever creates the task. The swarm's own intake paths use these templates (category `event` and `task_lifecycle`, full text in [`templates/event.md`](../../../work/prompt-variants/templates/event.md) and [`templates/task_lifecycle.md`](../../../work/prompt-variants/templates/task_lifecycle.md)):

| Source | Templates | Who receives it | Shape |
|---|---|---|---|
| Slack mention / DM | `slack.message.thread_context` + raw user text | lead | `<thread_context>…</thread_context>` then the user's message. Slack channel/thread ids travel as task metadata, not prompt text |
| Slack monitored channel | `task.trigger.channel_activity` | lead | see 3.1 |
| GitHub webhook | 14 `github.*` templates + `common.delegation_instruction` + `common.command_suggestions.*` | lead | non-overridable header `[GitHub PR #n] title`, body with From/Repo/Branch/URL/Context, then "⚠️ As lead, DELEGATE" and "💡 Suggested: /review-pr or /respond-github" |
| GitLab webhook | 4 `gitlab.*` templates + gitlab variants of the common blocks | lead | same shape with `glab` commands |
| Linear | `linear.issue.assigned` / `.reassigned` / `.followup` | lead | issue fields + instructions |
| Jira | `jira.issue.assigned` / `.commented` / `.followup` | lead | same |
| AgentMail | `agentmail.email.mapped_lead` / `.mapped_worker` / `.unmapped` / `.no_agent` / `.followup` | lead or mapped worker | email envelope + reply instructions |
| Kapso (WhatsApp) | `kapso.message.received` | lead | message + reply instructions |
| App action | `task.app.action` | configured agent | action prompt + `[App action] app= action= input=` |
| Heartbeat | `heartbeat.checklist`, `heartbeat.boot-triage` | lead | system status + HEARTBEAT.md snapshot + 8 numbered rules |
| Worker finished | `task.worker.completed` / `task.worker.failed` | lead | "review needed" with 200-char task + 500-char output, "Do NOT re-delegate" |
| HITL resolved | `hitl.follow_up` | requesting agent | questions + human answers |
| Budget / routing | `task.budget.refused`, `task.reroute.decision`, `task.pool.starved.decision` | lead | decision prompts |
| Lead `send-task` | free text | worker | whatever the lead wrote, guided by `system.agent.lead` "Task Routing" |

So a "Slack task" on a worker is: generic worker system prompt + `system.agent.worker.slack` block + the lead's free-text description (which usually quotes the Slack ask) + Slack metadata inherited via `parentTaskId`.

## 4. Observations for the iteration pass

Ordered by expected payoff. Each one is a candidate, not a decision.

1. **Memory recall is instructed four times.** `system.agent.filesystem` says "REQUIRED: memory-search at the start of EVERY task". `system.agent.seed_scripts` says "At every task start (do this FIRST): run task-context-gathering". `work-on-task` step 2 says memory-search again. The runner also injects `### Relevant Past Knowledge` into the turn. Pick one mechanism and drop the rest.
2. **Scripts guidance is a third of the base prompt (≈2.3k tokens)** and it is present for every task, including one-line Slack answers. `script_authoring_contract` (1k tokens) is reference material, a good candidate for a skill or `script-query-types` pointer instead of a system-prompt block.
3. **`system.agent.self_awareness` is Claude-specific and partly stale.** It says "Headless Claude Code process" and "--append-system-prompt" to codex, pi, opencode, and claude-managed sessions. Gate it on provider or rewrite neutrally.
4. **claude-managed gets the local-env composite.** Variant 09 still contains the `/workspace` filesystem block, `start-up.sh`, `HEARTBEAT.md`, and `memory directories` guidance although `hasLocalEnvironment=false` strips the identity files. The composite choice only looks at `hasMcp` and `pi`. A `hasLocalEnvironment` branch (or a `worker.managed` composite) would remove ~1.5k tokens of wrong instructions.
5. **Scripts-only lead contradicts itself.** Variant 12 lists `send-task`, `get-swarm`, `store-progress` in `system.agent.lead`, then `scripts_only_mode` says those tools "do NOT exist here". Either a scripts-only lead composite, or drop lead support for code-mode.
6. **Slack provenance rule appears three times** (`system.agent.slack`, `system.agent.worker.slack`, `task.worker.completed` item 2), worded differently each time.
7. **77 em dashes in `session-templates.ts`** while `system.agent.communication_style` bans em dashes. The prompt breaks its own style rule 56 times in the minimal render.
8. **Typo in the first line every agent reads:** `system.agent.role` says "your unique identified is {{agentId}}".
9. **Legacy gating when `serverCapabilities` is undefined** includes `services` (PM2 + port 3000 + service registry, 0.37k tokens) for every worker on an older server. Fine for compatibility, but worth a sunset date.
10. **`system.agent.worker` says "collaborate with other workers as needed"** but the messaging block that makes this possible is capability-gated and default-disabled. The sentence has no tool behind it on most servers.
11. **Repo guidelines have two copies:** the generic `system.agent.code_quality` block explains that a MANDATORY section may exist, and the `## Repository Context` block is the section. When no repo is attached, `code_quality` is 0.25k tokens about a section that is not there.
12. **`task.trigger.assigned` output instructions and `work-on-task` Completion section say the same thing.** One of them can go.
13. **Lead prompt duplicates the follow-up rule.** `system.agent.lead` "Follow-Up Tasks" and `task.worker.completed` both say "Do NOT re-delegate". Consistent, but the lead reads both on every follow-up.
