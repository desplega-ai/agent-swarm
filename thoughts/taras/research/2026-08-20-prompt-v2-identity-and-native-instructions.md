# Identity files and native instruction loading

Question: the base prompt inlines SOUL.md, IDENTITY.md, CLAUDE.md, TOOLS.md (agent-level) plus the
cloned repo's CLAUDE.md into every session's system prompt. Do the harnesses already load some of
these natively from disk, making the inline copy redundant? Where can injection be trimmed?

Related prior research: `thoughts/taras/research/2026-08-20-system-prompt-variants.md` (full prompt
assembly map, gates, and token sizes for all 13 rendered variants) and its generated artifacts in
`thoughts/taras/research/2026-08-20-prompt-variants/`. This doc focuses narrowly on the
identity/CLAUDE.md question that document flags but doesn't resolve.

Note on this file's location: the caller asked for
`thoughts/taras/research/2026-08-20-prompt-v2/identity-and-native-instructions.md`. The repo's
`validate-thoughts.py` PreToolUse hook hard-enforces a flat
`thoughts/{user}/research/YYYY-MM-DD-topic-slug.md` pattern (no subdirectories under `research/`), so
this file lives at the flattened path below instead.

## 1. Identity file lifecycle

Four agent-level files, one repo-level file:

| File | Disk path (worker) | Created at boot | Session-end sync back to DB | Size budget (write-time ratchet) |
|---|---|---|---|---|
| SOUL.md | `/workspace/SOUL.md` | `src/commands/runner.ts:5235-5244` writes `agentSoulMd` via `writeProfileFileFromDb` | `src/hooks/hook.ts` Stop hook `syncIdentityFilesToServer` (claude); `src/commands/profile-sync.ts` `buildIndependentIdentityPayloads` (all harnesses, called from `runner.ts` session-end, see below) | `SOUL_MD_MAX_CHARS = 10_000` chars, `src/utils/identity-field-budget.ts:3,7` |
| IDENTITY.md | `/workspace/IDENTITY.md` | `runner.ts:5236,5247-5253` | same as above | `IDENTITY_MD_MAX_CHARS = 10_000` chars, `identity-field-budget.ts:4,8` |
| TOOLS.md | `/workspace/TOOLS.md` | `runner.ts:5270-5277` | same | `BOOTSTRAP_MAX_CHARS = 20_000` chars (shared const from `base-prompt.ts:19`), `identity-field-budget.ts:10` |
| CLAUDE.md (agent-level) | `/workspace/CLAUDE.md` unconditionally (`runner.ts:5292-5299`); **additionally** `~/.claude/CLAUDE.md` for claude sessions only, written by the SessionStart hook (`hook.ts:1052-1059`, via `writeAgentClaudeMd` at `hook.ts:220-230`, backed up/restored by `backupExistingClaudeMd`/`restoreClaudeMdBackup` at `hook.ts:208-244`) | see above | `resolveClaudeMdPath()` (`src/commands/profile-sync.ts:389-392`) picks which on-disk copy is the sync source: an all-claude batch of completed sessions uses `CLAUDE_MD_PATH` (`~/.claude/CLAUDE.md`, `profile-sync.ts:303`); any non-claude session in the batch uses `WORKSPACE_CLAUDE_MD_PATH` (`/workspace/CLAUDE.md`, `profile-sync.ts:311`). Runner picks the path via `resolveClaudeMdPath(...)` at `runner.ts:4364,5425,5893`. | `BOOTSTRAP_MAX_CHARS = 20_000` chars, `identity-field-budget.ts:9` |
| Repo CLAUDE.md | `<clonePath>/CLAUDE.md`, e.g. `/workspace/personal/repos/<repo>/CLAUDE.md` | Cloned by git, read (not written) by the runner at `runner.ts:183-191` | n/a (not agent-owned; it's the repo's own file) | `REPO_CLAUDE_MD_MAX_CHARS = 12_000` chars, `src/prompts/base-prompt.ts:41`, applied only to the copy injected into the prompt, never to the file on disk |

Defaults for a brand-new agent (no DB row yet) are generated by `src/prompts/defaults.ts`:
`generateDefaultClaudeMd` (:9), `generateDefaultSoulMd` (:56), `generateDefaultIdentityMd` (:116),
`generateDefaultToolsMd` (:154). `runner.ts:5136-5157` falls back to a cached prompt-template
(`cachedTemplate.files.soulMd`/`identityMd`) first, then these generators, and persists whichever
default it picked back to the profile (`runner.ts:5164-5165,5182`) so it becomes the DB baseline.

**Sync-to-DB path.** Two independent mechanisms exist, both writing to the same `/api/agents/:id/profile`
endpoint:
- Claude-only: `src/hooks/hook.ts` Stop/PostToolUse hooks call `syncClaudeMdToServer` (:666-680, reads
  `CLAUDE_MD_PATH` = `~/.claude/CLAUDE.md`) and `syncIdentityFilesToServer` (:691-710ish, reads
  `/workspace/SOUL.md` / `/workspace/IDENTITY.md`, `IDENTITY_FILE_MIN_LENGTH = 500` guards against
  short-payload corruption, :688).
- Harness-agnostic backstop: `src/commands/profile-sync.ts`, invoked from `runner.ts` at session end
  (comment at `runner.ts:4338-4356`: "The Claude plugin Stop hook and the pi extension sync
  SOUL/IDENTITY/TOOLS/CLAUDE.md + start-up.sh on their own, but codex/opencode have no such path and
  pi's can silently not-fire (2026-06-01 regression)"). This is idempotent (content-hash gated) and
  runs for every finished local-environment session regardless of harness.
- Baseline-hash guard: `runner.ts:5303-5315` records SHA-256 baselines of the DB content right after
  writing it to disk (`writeIdentityBaselines`), so session-end sync only pushes a field back to the
  DB if the on-disk content actually changed during the session (prevents clobbering a concurrent
  Lead `update-profile` edit).
- Audit tool: `src/commands/profile-sync-audit.ts` (`runProfileSyncAudit`) compares disk vs DB and
  exits 2 if any field diverges — a drift detector, not a sync path itself.
- Server-side write cap: `MAX_PROFILE_FILE_LENGTH = 256 * 1024` chars, `src/utils/constants.ts:6`
  (much looser than the per-field ratchet in `identity-field-budget.ts`; the ratchet is the real gate).
- E2E gate: `scripts/e2e-identity-field-budget.ts` boots a real HTTP/MCP server and drives the ratchet
  through both REST and MCP `update-profile`, asserting rejections by re-reading the persisted row.

**UI edit surface.** `apps/ui/src/pages/agents/[id]/page.tsx:56,69-72` defines the four editable tabs
(`soulMd`→"SOUL.md", `identityMd`→"IDENTITY.md", `claudeMd`→"CLAUDE.md", `toolsMd`→"TOOLS.md", plus
`setupScript`/`heartbeatMd`). The fields flow through `apps/ui/src/api/types.ts:56-59`,
`apps/ui/src/api/client.ts:288-291`, `apps/ui/src/api/hooks/use-agents.ts:80-83`.

**Which harnesses get which files.** All four agent-level files are written to `/workspace/*.md` for
every local-environment harness (`runner.ts:5234-5299`), independent of provider. The extra
`~/.claude/CLAUDE.md` materialization is claude-only (Claude Code plugin hook, not reachable from
codex/opencode/pi, which have no Claude-Code-style hook system — see `runner.ts:4338-4339` comment).
Non-local providers (`hasLocalEnvironment=false`: `claude-managed`, `devin`) skip the whole
`/workspace` write and the identity section entirely (`base-prompt.ts:211-222`, "Simplified identity
for remote providers — no self-evolution, no /workspace files").

## 2. Native instruction-file loading per harness

| Harness | Loads agent CLAUDE.md natively? | Loads repo CLAUDE.md natively? | Verdict | Evidence |
|---|---|---|---|---|
| **claude** | **Yes**, twice over | **Yes** | Redundant injection confirmed | See below |
| **codex** | No (swarm manages it) | Partially — swarm prepends into it | By design, not redundant | See below |
| **opencode** | Unknown / not swarm-managed | Unknown | Unverified | See below |
| **pi** | Partial, via a symlink trick | Partial, same trick | Redundant for the symlinked case | See below |

### claude — Yes (high confidence)

Two independent native-load paths exist, both landing before/around the same session the swarm
also injects `## Agent Instructions` into:

1. **Ancestor-directory CLAUDE.md.** `effectiveCwd` resolution priority is
   `task.dir > repoContext.clonePath > process.cwd()` (`runner.ts:5970-5992`, comment at :5970).
   `process.cwd()` at worker boot is `/workspace` (`Dockerfile.worker:433,650` set `WORKDIR
   /workspace` in both the `worker-slim` and `worker-full` leaf stages; `docker-entrypoint.sh` never
   `cd`s elsewhere before `exec tini -- gosu worker "$WORKER_BOOTSTRAP"`, and logs "Working
   Directory: /workspace" at `docker-entrypoint.sh:373`). For a repo task, `clonePath` follows the
   convention `/workspace/personal/repos/<repo-name>` (`runner.ts:5501,5950`). `/workspace/CLAUDE.md`
   — the file the runner unconditionally writes at `runner.ts:5292-5299` for every local harness —
   is therefore a direct **ancestor directory** of the clone path. Claude Code's CLAUDE.md discovery
   walks the directory ancestry chain and applies every CLAUDE.md found along it (confirmed via
   Context7 `/anthropics/claude-code` docs: "each file is governed only by CLAUDE.md files along its
   directory ancestry chain"). So `/workspace/CLAUDE.md` (the agent's own instructions) is picked up
   automatically by Claude Code even with zero prompt injection, whenever cwd is inside `/workspace`.
2. **User-level `~/.claude/CLAUDE.md`.** The Claude Code plugin's `SessionStart` hook
   (`src/hooks/hook.ts:1052-1059`) writes `agentInfo.claudeMd` straight into `~/.claude/CLAUDE.md`
   (`writeAgentClaudeMd`, :220-230) before the session even starts working, and the `Stop` hook
   restores the pre-session backup afterward (:1310,1343, `restoreClaudeMdBackup` :235-244).
   `~/.claude/CLAUDE.md` is Claude Code's documented **user-level memory** file, always loaded
   (Context7 `/websites/code_claude` "Claude Directory" doc: "Claude Code retrieves instructions,
   settings, skills, subagents, and memory from both the project directory and the user's home
   directory"). HOME is `/home/worker` in the container (`Dockerfile.worker:90`, `ENV
   HOME=/home/worker`), so this is `/home/worker/.claude/CLAUDE.md` in practice.
3. **This is the actual CLI, not the Agent SDK's opt-in `settingSources`.** `claude-adapter.ts`
   `Bun.spawn`s the `claude` binary directly (`claudeBinaryArgv` default `["claude"]`, resolved via
   `CLAUDE_BINARY`, :584,725-736) in headless print mode (`-p <prompt>`, :746) with
   `--append-system-prompt-file`/`--append-system-prompt` (:757-760, `Bun.spawn(cmd, {cwd:
   this.config.cwd, ...})` at :619-621). It never passes a `--setting-sources` restriction. The
   Context7 docs distinguish the CLI (loads project + user CLAUDE.md by default) from the Agent SDK's
   `query()` (`settingSources` must be explicitly set to `["user", "project"]` to get the same
   behavior) — the swarm's own claude sessions are on the CLI path, so default native loading applies
   with no extra config needed.

Net effect: for claude sessions, both `## Agent Instructions` (base-prompt.ts injection) and the
native CLAUDE.md load deliver the same content, through two different channels, in the same session.

### codex — No, by design (not redundant)

`src/providers/codex-agents-md.ts` header comment (:1-34): "Codex reads `AGENTS.md` from the session
cwd at startup and uses its contents as the agent's base instructions. There is no
`ThreadStartParams.systemPrompt` / `developerInstructions` equivalent... so the only way to inject our
per-session `config.systemPrompt` is to write it into `AGENTS.md`". `writeCodexAgentsMd` (:56)
manages a delimited `<swarm_system_prompt>...</swarm_system_prompt>` block inside `AGENTS.md`. If the
repo already ships a `CLAUDE.md` and no `AGENTS.md`, the block is **prepended to the CLAUDE.md
contents** and the merged file becomes `AGENTS.md` (:64-65, :18-21 comment) — Codex sees the swarm's
system prompt plus the repo's own CLAUDE.md in one file, so there is no separate native load to
duplicate against; the swarm's `AGENTS.md` write **is** the delivery mechanism, not a redundant copy
of one. No comment or code claims Codex walks ancestor directories for `AGENTS.md`.

### opencode — Unknown

`src/providers/opencode-adapter.ts` writes a per-task **agent definition** file at
`.opencode/agents/swarm-<taskId>.md` containing `config.systemPrompt` (:713-721), referenced later
when building the opencode session config (:941). Grepping the file for `AGENTS.md`/`CLAUDE.md`
returns zero matches — the adapter does not read, write, or manage either file. Whether opencode's own
runtime independently discovers an `AGENTS.md`/`CLAUDE.md` in cwd (as a documented opencode feature,
separate from the swarm's per-task agent file) is not established anywhere in this codebase; the only
adjacent evidence is `thoughts/taras/research/2026-05-28-context-mode-mcp-setup-across-harnesses.md:57,198`,
which notes the context-mode opencode plugin does an "AGENTS.md scan" on first tool use for its own
skill-discovery purposes — not proof either way for instruction loading. Marking this **Unknown**;
would need an opencode-docs check (not done here) or an empirical test (drop an `AGENTS.md` in a repo
clone, run an opencode task with no system-prompt override, see if it's honored).

### pi — Partial via symlink

`src/providers/pi-mono-adapter.ts:1209` passes the swarm's system prompt through
`DefaultResourceLoader({ appendSystemPrompt: config.systemPrompt ? [config.systemPrompt] :
undefined, ... })` — an explicit append, same pattern as claude's `--append-system-prompt`. Separately,
`createAgentsMdSymlink` (:614-620, comment "Manage AGENTS.md symlink for pi-mono CLAUDE.md
compatibility") symlinks `AGENTS.md -> CLAUDE.md` inside cwd whenever a `CLAUDE.md` exists there and no
`AGENTS.md` does yet, called at session start (:1080-1081, "1. Set up AGENTS.md symlink"),
cleaned up via `cleanupAgentsMdSymlink` (:629-637, guarded to only remove real symlinks). This implies
pi-mono natively reads `AGENTS.md` (not `CLAUDE.md`) from cwd, and the swarm's symlink trick is there
specifically so a **repo's own CLAUDE.md** becomes visible to pi without the swarm having to inject
it. That repo file is separate from the swarm's agent-level CLAUDE.md (which is delivered purely via
`appendSystemPrompt`, no symlink or native-load path). No comment claims pi walks ancestor
directories.

## 3. Cost estimate

From `thoughts/taras/research/2026-08-20-prompt-variants/00-INDEX.md` (generated with **sample**
identity files, a few lines each — not the worst case) the baseline composite + conditional blocks
run 5.9k-8.9k tokens across the 13 variants (row "01 Claude worker, minimal" = 6,407 tokens for 25,627
chars, i.e. ~4.0 chars/token — consistent across the set).

Worst-case *added* chars from the identity + repo-CLAUDE.md sections specifically, using the hard
caps in `base-prompt.ts` and `identity-field-budget.ts`:

| Section | Cap (chars) | ~Tokens (÷4) |
|---|---:|---:|
| SOUL.md (`## Your Identity`) | 10,000 (write-time ratchet, not re-truncated at render) | ~2,500 |
| IDENTITY.md (`## Your Identity`) | 10,000 (same) | ~2,500 |
| Repo CLAUDE.md (`## Repository Context`) | 12,000 (`REPO_CLAUDE_MD_MAX_CHARS`, `base-prompt.ts:41`) | ~3,000 |
| Agent CLAUDE.md (`## Agent Instructions`) | 20,000 (`BOOTSTRAP_MAX_CHARS`, `base-prompt.ts:19`) | ~5,000 |
| TOOLS.md (`## Your Tools & Capabilities`) | 20,000 (same const, gets whatever's left of the total budget after CLAUDE.md, `base-prompt.ts:426-427`) | ~5,000 |
| **Sum if every cap is hit simultaneously** | **72,000** | **~18,000** |

That sum is smaller than it could naively be because `BOOTSTRAP_TOTAL_MAX_CHARS = 120,000`
(`base-prompt.ts:33`) caps the **entire assembled prompt**, not just these sections — repo CLAUDE.md
is protected/never truncated below 12k, agent CLAUDE.md is truncated next if the total budget is
tight, and TOOLS.md is truncated first/dropped entirely if nothing is left
(`base-prompt.ts:413-430`, priority comment "Agent CLAUDE.md > tools"). The 120k-char /
~30k-token ceiling exists specifically so the whole prompt (composite ~6-9k tokens + everything
above) can never re-trigger the 2026-05-28 Picateclas `posix_spawn` E2BIG / `MAX_ARG_STRLEN` crash
(`base-prompt.ts:21-32`).

So: **worst case, identity + repo-CLAUDE.md injection alone can add ~18k tokens** (72k chars) to every
single task's system prompt, on top of a ~6-9k token baseline — roughly doubling to tripling prompt
size for an agent with maxed-out SOUL/IDENTITY/CLAUDE/TOOLS files and a large repo CLAUDE.md. This
repeats on **every task**, not once per session lifetime, because the system prompt is rebuilt per
task (`buildSystemPrompt()`, noted in `2026-08-20-system-prompt-variants.md:25`).

## 4. Options to reduce injection

**(a) Inject only SOUL.md + IDENTITY.md; reference CLAUDE.md/TOOLS.md by path.**
Saves up to ~10k tokens (CLAUDE.md + TOOLS.md caps) per task. Breaks: codex and opencode have no
other path to see agent CLAUDE.md/TOOLS.md content at all (codex only gets what's written into
`AGENTS.md`; opencode only gets what's in the per-task agent file) — for those two providers this is
not "redundant trim," it's "delete the only delivery channel." Would need codex/opencode to
additionally read `/workspace/CLAUDE.md`/`/workspace/TOOLS.md` themselves, which they don't do today
(section 2). Also breaks `identity-field-budget.ts:47`'s own stated invariant ("tail... only reaches
harnesses with a native CLAUDE.md loader") if the *whole* field stops being injected, not just the
tail.

**(b) Inject nothing; rely on native loading; keep a one-line pointer.**
Only safe for claude, where native loading is confirmed redundant (section 2). Breaks codex (no
native AGENTS.md ancestor-walk claimed anywhere, and codex's only channel for the swarm prompt IS the
AGENTS.md write — removing injection removes the system prompt entirely, not just the identity part).
Breaks opencode (verdict Unknown — could silently drop instructions with no fallback). Breaks pi's
agent-level CLAUDE.md (delivered only via `appendSystemPrompt`, no symlink covers it) — only pi's view
of the *repo's* CLAUDE.md would survive via the AGENTS.md symlink.

**(c) Keep inline only for harnesses that do not auto-load.**
Given section 2's findings: drop/shrink the `## Agent Instructions` injection for **claude only**
(confirmed double-delivered), keep it as-is for codex, opencode, pi. This is the option best supported
by evidence gathered here — it's a single-harness, single-field change with a documented mechanism
(ancestor CLAUDE.md walk + `~/.claude/CLAUDE.md` SessionStart write) rather than an assumption. It
does NOT touch SOUL.md/IDENTITY.md (no evidence any harness loads those natively under any name) or
TOOLS.md (no harness has a "TOOLS.md" convention). Residual risk: confirm empirically (not just via
docs) that Claude Code's headless `-p` mode with `--append-system-prompt-file` set actually still
performs the ancestor CLAUDE.md walk and does not suppress it — the docs found here describe the
general CLI/product behavior, not this exact flag combination.

**(d) Merge the four files into one or two.**
E.g. merge TOOLS.md into CLAUDE.md (both already share the same 20k-char budget and both only exist
for local-env harnesses). Saves a heading + duplicate truncation-footer overhead, not much token
volume (the cap is shared already, `IDENTITY_FIELD_BUDGETS.claudeMd === IDENTITY_FIELD_BUDGETS.toolsMd
=== BOOTSTRAP_MAX_CHARS`). Breaks: the UI's four-tab editing model
(`apps/ui/src/pages/agents/[id]/page.tsx:69-72`), the independent-sync guarantee in
`profile-sync.ts` ("Keep identity-file sync independent: one rejected ratcheting-budget write must
not discard valid edits to other files from the same session", :353-356 area), and every test that
asserts the four headings/fields independently (`src/tests/base-prompt.test.ts` — extensively pins
`"## Your Identity"` (:149,158,164), `"## Agent Instructions"` (:172,177,196), `"## Your Tools &
Capabilities"` (:186), plus a dedicated truncation-priority test at :410-439 that specifically
exercises CLAUDE.md-before-TOOLS.md ordering, and the repo-CLAUDE.md cap test at :456-486).
`src/tests/prompt-template-session.test.ts` does not pin these headings (it tests
`session-templates.ts` composites, a different file) so it's not a blocker for (d), but
`base-prompt.test.ts` would need a rewrite. `src/tests/self-improvement.test.ts` doesn't touch
SOUL/IDENTITY/TOOLS/CLAUDE.md headings at all (it tests memory/self-awareness), not a blocker.

**Recommendation.** Do (c) for claude only, since it's the one option backed by a directly-observed
double-delivery mechanism rather than a guess. Before shipping it: empirically verify the ancestor
walk survives `-p` + `--append-system-prompt-file` (spawn a real headless session, drop a sentinel
line in `/workspace/CLAUDE.md`, confirm the model can quote it with zero prompt injection). Leave (a)
and (b) off the table until opencode's native-loading behavior is confirmed (currently Unknown) and
codex/opencode get an alternate read-path for CLAUDE.md/TOOLS.md if injection is trimmed. Skip (d);
the token savings are marginal against real UI/sync/test churn — not worth it on its own, though
worth revisiting alongside a broader identity-file redesign if one happens anyway.
