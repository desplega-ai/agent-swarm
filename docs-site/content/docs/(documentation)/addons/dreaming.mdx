---

**Dreaming** is the swarm's nightly reflection pass. Once a day, every live agent reads a slice of its own last 24 hours — failed tasks, retries, tool usage, memory usefulness, its current context files — and proposes a small set of concrete changes. The Lead critiques the pooled proposals in a single turn, and one mechanical script applies whatever survived.

The output is not a report. It is edits: rules added to `CLAUDE.md`, gotchas added to `TOOLS.md`, memories written or deleted, skills created or fixed, stale duties removed from `HEARTBEAT.md`. The Slack post is only the receipt.

<Callout type="info">
  Dreaming is also referred to as **compounding** — the earlier name. You will still see it in older memories, schedules, and Slack history, and in the `compound-insights` script and the `daily-compounding-reflection` schedule template it grew out of.
</Callout>

## Architecture

<Mermaid chart={`flowchart TD
  G["gather<br/>cheap preflight: config + activity + roster"] --> P{"proceed?"}
  P -- false --> D["done"]
  P -- true --> GR["gather-rich<br/>full evidence, as Lead"]
  GR --> RP{"rich-proceed?"}
  RP -- false --> D
  RP -- true --> HS["hygiene-snapshot<br/>PR snapshot"]
  HS --> R["reflect<br/>foreach agent"]
  HS --> S["skills lane"]
  HS --> H["hygiene lane"]
  R --> C["critique<br/>Lead, one turn"]
  S --> C
  H --> C
  C --> A["dream-apply<br/>sole mutator"]
  A --> RC["dream-receipt"]
  RC --> D
`} />

| Node | Type | What it does |
| --- | --- | --- |
| `gather` | script (`dream-gather`) | Cheap unprivileged preflight: the `DREAMING_ENABLED` setting, the activity signal, and the live agent roster (including which agent is Lead). Disabled swarms, quiet days, and installs with no Lead all stop here. |
| `proceed?` | code-match | Routes to `done` unless dreaming is enabled **and** the window had activity. A quiet day costs exactly one cheap script execution. Activity means tasks the swarm ran that Dreaming did not create — its own reflection and critique tasks are excluded, so a quiet swarm stays quiet instead of dreaming about its own dreaming. |
| `gather-rich` | script (`dream-gather`, as Lead) | The full evidence pass — swarm-wide insights, blocker sweep, profile anchor inventory — run under the Lead's identity, re-gated by `rich-proceed?`. |
| `hygiene-snapshot` | script (`gh-pr-snapshot`) | Snapshots the rotating pull-request target (skips gracefully when there is none), then fans out the three lanes. |
| `reflect` | foreach → agent task | One reflection task per live agent, fanned out in parallel. Each agent reads its own `dream-agent-slice` and proposes deltas. |
| `skills` | agent task (Lead) | Reviews skill inventory versus actual invocation — proposes new, updated, or better-described skills. |
| `hygiene` | agent task (Lead) | Recurring-duty upkeep: what belongs in `HEARTBEAT.md`, what's stale, whose turn it is on rotation. |
| `critique` | agent task (Lead) | Pools every lane's proposals, removes duplicates and drift, arbitrates conflicts, and emits the approved delta set. A lane that failed contributes nothing rather than blocking the run. |
| `apply` | script (`dream-apply`, as Lead) | The **only** node that mutates state. Validates each delta, splices anchored profile edits, writes memories and skills. Every applied edit is recorded with its file, anchor, op, and a content hash, and leaves a per-run idempotency receipt in KV — a retried or crash-recovered apply skips deltas it already applied instead of duplicating them. |
| `receipt` | script (`dream-receipt`, as Lead) | Records what happened as a memory, and posts it to Slack if a channel is configured. |

The parent `reflect` node owns the join: the run cannot reach `critique` until every agent's reflection task is terminal. A failed reflection lane does not kill the run — the failure is carried into the aggregate and the other agents' proposals still reach critique.

### The invariant

**Workers propose, the Lead critiques, only `dream-apply` mutates.**

No reflection task edits a profile, writes a memory, or creates a skill. Every lane's only output is structured JSON. This is what makes the pass reviewable: a single script performs every write, applies one uniform set of guards, and produces one auditable list of what landed and what didn't.

## Deltas

The unit of change is a **ReflectionDelta**. There are four kinds:

| Kind | Target | Notes |
| --- | --- | --- |
| `profile-op` | `SOUL` / `IDENTITY` / `CLAUDE` / `TOOLS` / `HEARTBEAT` | Anchored section edit: `append-under`, `replace-section`, or `remove-section`. |
| `memory` | Swarm memory | `write` (needs content) or `delete` (needs the memory id). `scope` may only be `swarm` — the write path stores swarm-scoped memory, so an agent-scoped request is held rather than silently published. A `delete` only applies when the memory actually belongs to the delta's `agentId`; a mismatched or unknown id is held. |
| `skill` | Skills catalog | `create` or `update`; content is the whole skill body. `scope` may only be `swarm` — the apply runs as the Lead, so an agent-scoped skill would bind to the Lead identity instead of the lane that proposed it. |
| `hygiene` | `HEARTBEAT` | Same anchored ops, plus an optional rotation-cursor advance. |

Agents learn how to produce these from the seeded **`dreaming` skill**, which is the runtime playbook for a reflection lane: evidence rules, the field contract, anchor discipline, and which file a given piece of knowledge belongs in.

### Anchored edits

Profile changes are surgical by design — whole-file rewrites destroy accumulated evolution. An op names an **exact H2 heading** as its anchor, quoted verbatim from the profile text the agent was given, and the splice engine fails closed:

- The anchor must be an exact `## ` heading and must match **exactly one** section. Zero matches or a duplicated heading is refused.
- `content` may not introduce new `## ` headings — new anchors are never created implicitly.
- `append-under` inserts at the **end** of the section, just before the next H2.
- `remove-section` deletes the heading and everything down to the next H2.
- `SOUL` and `IDENTITY` have a 200-character floor; a splice that would take either below it is refused.
- Headings inside fenced code blocks are not anchors.

## HELD, APPLIED, DEFERRED

`dream-apply` sorts every approved delta into three buckets:

- **APPLIED** — the write landed.
- **HELD** — refused *before* any write. Schema violation, unexpected field, anchor not found, ambiguous anchor, missing content, content introducing H2s, or the `SOUL`/`IDENTITY` length floor. Nothing changed.
- **DEFERRED** — the delta was valid but the write itself errored (a downstream tool failure).

HELD is the fail-loud surface, and it appears with its reason on the same day's receipt. A held delta is not retried automatically — the next dream re-derives its proposals from fresh evidence, and a correctly re-anchored version simply applies then. A long HELD list means the proposals were not grounded in the agents' actual slices.

## Configuration

Both keys live on **Settings → Configuration**.

| Key | Type | Default | Effect |
| --- | --- | --- | --- |
| `DREAMING_ENABLED` | boolean | *(absent — enabled)* | When set to `false` — as a stored row **or** as a deployment environment variable — the run stops at the gate node. This is the runtime kill switch, not the on switch: with no value a *triggered* run proceeds, but the `dream-daily` schedule still ships disabled, so nothing fires until you enable it. |
| `DREAMING_SLACK_CHANNEL` | string | *(absent — no post)* | Slack channel id for the nightly receipt. With no value, the receipt is still written to memory; it is just not announced. |

<Callout>
  The gate resolves the **effective** value: setting `DREAMING_ENABLED=false` in the deployment environment works as an emergency kill switch even with no stored row, because the config read falls back to the server's environment for catalog keys. The standard precedence still applies — env wins at boot, a value saved on Settings → Configuration wins after the config reload it triggers.
</Callout>

A Slack channel id is configuration, not a credential, so it belongs on this page rather than the Secrets page.

## The receipt

Every dream that gets past the gate produces a receipt, stored as a memory and — if `DREAMING_SLACK_CHANNEL` is set — posted to Slack:

```text
🌙 Dreaming — 2026-08-04
Run: 4f1c9d2e-…

APPLIED (3)
8f2c1d34-…: profile-op — Same mis-read-assertion failure twice in 24h.
8f2c1d34-…: memory — Rediscovered the same non-existent-tool dead end.
a71b0e55-…: hygiene — Backfill completed; duty is stale.

HELD (1)
a71b0e55-…: profile-op — anchor is ambiguous: ## Conventions

DEFERRED (0)
- none
```

Each line is `<agent id>: <delta kind> — <reason>`; empty buckets render `- none`.

<Callout type="info" title="Receipt memories carry a prefix today">
  The apply and receipt steps run under the Lead's identity, and the receipt is persisted through the learning-injection path, which prefixes the stored memory's title with `Lead feedback: best-practice — `. The receipt body is stored verbatim. The prefix is a current implementation artifact, not part of the receipt format — search memory for `Dreaming` rather than matching on the title.
</Callout>

## Scheduling, disabling, retiming

Dreaming ships as an [add-on](/docs/addons): a workflow named `dream`, a daily schedule that fires it, the `dreaming` skill, six catalog scripts (`dream-gather`, `dream-agent-slice`, `dream-apply`, `dream-receipt`, plus the shared `compound-insights` and `gh-pr-snapshot`), and the two configuration keys above. Everything is seeded on first boot.

<Callout type="warn" title="The schedule ships disabled">
  Dreaming edits agent profiles, memories, and skills, so a fresh install does not acquire it silently. Every piece seeds — you can open the `dream` workflow, read the scripts, and trigger a run by hand — but nothing fires on a timer until you **enable the `dream-daily` schedule** in the dashboard. Enabling it is also what pins it: `enabled` is part of the preservation hash, so your choice survives every later release.
</Callout>

- **Turn it on** — enable the `dream-daily` schedule (dashboard → Schedules). It runs daily at 02:10 UTC.
- **Try it once first** — trigger the `dream` workflow manually and read the receipt before committing to a nightly cadence.
- **Pause it** — set `DREAMING_ENABLED = false`. The schedule still fires; the run exits at the gate after one cheap script execution. Reversible at any time.
- **Stop it entirely** — disable the schedule again.
- **Retime it** — change the schedule's cron or its timezone.

All three survive restarts, redeploys, and upgrades. Editing a seeded entity — flipping `enabled`, changing the cron, reworking the workflow graph — marks it as yours, and the seeder never overwrites it again. See [Add-ons](/docs/addons) for the full preservation contract and how to return an entity to the shipped version.

<Callout type="warn">
  Because `enabled` and the cron expression are part of the preservation hash, a deliberate disable is permanent until you re-enable it yourself. That is the intended behavior — an upstream change to the shipped schedule will never silently turn dreaming back on.
</Callout>
