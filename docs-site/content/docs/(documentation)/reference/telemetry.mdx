Agent Swarm sends usage telemetry to the maintainers to help them understand usage patterns and improve the product. Telemetry is **on by default** and you can turn it off at any time (see [How to opt out](#how-to-opt-out)). Setup does not ask you to opt in, and it has no telemetry toggle.

This page lists every field that leaves your install.

## What is collected

Telemetry tracks lifecycle and operational events. It does not include task descriptions, prompts, outputs, agent names, email addresses, user names, or error messages. The only free-text values it carries are ones you set yourself, such as `SWARM_ORG_NAME`, and the email **domain** of your admin (see [Identity context](#identity-context)).

IDs below (`taskId`, `agentId`, `workflowId`) are random UUIDs generated by your install.

The table below is generated from the event catalog that the telemetry endpoint enforces (`src/telemetry-contract`). An event or property that is not listed here is rejected by the endpoint, and a build that emits one fails to compile. Events with the `ui` emitter, plus `lead.captured`, `skill.invoked` and `session.steered`, are reserved in the catalog and are not sent by this release. Dashboard events still go through the path described under [Dashboard notification events](#dashboard-notification-events).

### `trigger_surface`

Surface that started a chain of work: agent-swarm's AgentTaskSourceSchema values plus other.

Values: `slack`, `ui`, `api`, `mcp`, `github`, `gitlab`, `linear`, `jira`, `agentmail`, `schedule`, `workflow`, `system`, `other`.

### Fields on every event

Each event is a JSON envelope with these top-level fields:

- `schema_version` — always `2`
- `product` — always `agent-swarm`
- `event` — the event name from the table above
- `occurred_at` — timestamp
- `source` — the emitter (`api-server` or `worker`)
- `actor_mode` — always `anonymous`
- `actor_anonymous_id` — the installation ID (see [Identifiers](#identifiers))
- `context` — the identity block described under [Identity context](#identity-context)

Every event also adds these to `properties`. They are the same facts `context` carries, kept under their older names while existing dashboards move over:

- `swarmVersion` — the Agent Swarm version
- `is_cloud` — boolean, whether the event came from a cloud-hosted swarm or a self-hosted install. True when `MCP_BASE_URL` points at a host we operate or `SWARM_CLOUD` is set. The hostname itself is never sent.
- `is_e2b` — boolean, whether the process runs inside an E2B sandbox
- `has_embedding_key` — boolean, whether an embedding-capable key (`EMBEDDING_API_KEY` or `OPENAI_API_KEY`) is configured, i.e. whether semantic memory search is likely enabled
- `has_slack_channel` / `has_email_channel` / `has_notification_channel` — booleans indicating whether an outbound notification channel (Slack, AgentMail email, or either) is configured. Presence only — never a token, channel ID, or address.
- `install_method` — enum: `onboard_interactive`, `onboard_noninteractive`, `e2b`, or `manual`. Which entry point produced this install.

And these to `metadata`:

- `transport` (always `https`) and `environment` (`production` by default; override with `DESPLEGA_TELEMETRY_ENV`)
- `is_cloud` — boolean, from `SWARM_CLOUD`
- `organization_id` (optional) — your `SWARM_ORG_ID`, when set
- `organization_name` (optional) — your `SWARM_ORG_NAME`, when set
- `install_preset` (optional) — the onboard wizard preset used (`dev`, `content`, `research`, `solo`, or `custom`), when the install went through the wizard. Allow-listed against the wizard's known preset IDs — any other value (including free text accidentally placed in `INSTALL_PRESET`) is omitted rather than forwarded.
- `install_created_at` (optional) — ISO timestamp of when this install's identity was first minted, persisted once alongside the installation ID. Only set when this process genuinely mints a new installation ID; an existing installation ID with no stored anchor emits this field as **absent**, not back-filled with the current time — absence means "pre-existing install, anchor unknown". Use `min(occurred_at)` per `installation_id` in ClickHouse as the real anchor for that population.

### Identity context

`context` says which organization and which person an event belongs to, without carrying anything that identifies them directly.

| Field | What it holds | How it is derived |
|---|---|---|
| `org_id` | An organization ID | `SWARM_ORG_ID` when it is set to a valid ID (cloud deployments). Otherwise a random `org_` + 16 hex characters, minted once and stored as `telemetry_org_id`. |
| `org_name` | The name you gave the organization | `SWARM_ORG_NAME`, when set. `null` otherwise. |
| `org_domain` | The email **domain** of your admin, such as `example.com` | The domain of the earliest-created active user who has an admin grant, falling back to the earliest active user with an email. Lowercased, stored as `telemetry_org_domain`, and recomputed when a user changes and hourly. The address itself is never sent. |
| `user_ref` | A pseudonymous reference to the person who caused the event | `u_` plus the first 32 hex characters of `sha256(installation ID + ":" + user ID)`. Stable inside your install, different on every other install, and not reversible to the user. `null` for events nobody caused (server start, schedules, heartbeat). |
| `user_role` | `admin` or `member` | From the user's role grants. `null` when `user_ref` is `null`. |
| `plan` | `self-host-free` or `cloud` | `cloud` for a cloud deployment, else `self-host-free`. |
| `deployment` | `self-host`, `cloud` or `e2b` | Where the process runs. |
| `swarm_version` | The Agent Swarm version | `package.json`. |
| `install_method` | How the install was produced | Same as the property of the same name. |
| `install_preset` | The onboard wizard preset | Same as the `metadata` field. `null` when there is none. |
| `acquisition_source` | Reserved | Always `null` today. |

What is never sent: email addresses (only the domain of one address), user names, raw user IDs, task content, prompts or outputs.

#### Which surface started the work

Task and session events carry `trigger_surface`: the surface that started the **whole chain of work** (`slack`, `ui`, `api`, `mcp`, `github`, `gitlab`, `linear`, `jira`, `agentmail`, `schedule`, `workflow`, `system`, or `other`). It is the `source` of the root task. A Slack request that the lead splits into five worker tasks counts as six Slack tasks, and every `task.*` and `session.*` event of the chain reports `slack`. Tasks the swarm creates for itself, such as the heartbeat checklist and boot triage, are `system`. `task_source` keeps the raw `source` of each task on its own, for debugging delegation.

#### Daily organization snapshot

Once a day each install sends one `org.snapshot` event from the API server. It carries counts only: active and suspended users, admins, users who can log in, users with a linked Slack, GitHub, GitLab, Linear, Jira or other identity, users who requested a task in the last seven days, and registered agents. It carries no names, email addresses or IDs. The send time is stored as `telemetry_last_snapshot_at`, so a restart does not send a second one the same day.

### Dashboard notification events

The dashboard sends its own small events from the browser to the feedback endpoint (`https://proxy.desplega.sh/v1/feedback`, overridable with the `feedback_endpoint` config key). They fire when someone opens the notification bell or acts on a notification card, and they honor the same opt-out as the server events above.

Each carries:

- `submission_id` — a random UUID per event
- `user_id` — the dashboard user's ID
- `install_id` and `installed_at` — the installation ID and its anchor timestamp
- `org_name` — the organization name shown in the dashboard header (`SWARM_ORG_NAME`, or `Swarm` when unset)
- `swarm_version`
- `newsletter_consent` — always `false`. Notification events never subscribe anyone to a newsletter.
- `message` — `[notification_event] key=<notification> action=<view|dismiss|submit|already_have_one>`, plus the email **domain** (never the address) on `submit`
- `submitted_at`

A notification card that asks for your email, and the feedback dialog, are different. Those send what you type and only when you submit them. They are not telemetry, so the opt-out does not block them.

## Identifiers

- **Installation ID.** Each installation generates a random, opaque identifier (e.g. `install_a1b2c3d4e5f6g7h8`), stored in the `swarm_config` table. It is not derived from your hostname, domain, or account, and it stays the same across restarts so events from one install link together.
- **Organization identity.** The installation ID is random, but events are not anonymous to your organization. Every event carries an organization ID (`org_id`), the organization name when you set `SWARM_ORG_NAME`, and the email domain of your admin (`org_domain`), so they are attributable to your organization. Cloud deployments set `SWARM_ORG_ID`. The setup wizard's "name your swarm" step and the dashboard's organization-name prompt set `SWARM_ORG_NAME`. Leave `SWARM_ORG_NAME` unset, or opt out, if you do not want to share an organization name.
- **People.** Events caused by a person carry a pseudonymous `user_ref`, never an email address or a name. See [Identity context](#identity-context).
- **No IPs logged.** The telemetry endpoint (`proxy.desplega.sh`) does not store client IP addresses.
- **No auth required.** Events are sent in anonymous actor mode with no authentication headers.

## Installation ID mechanism

On first startup, the telemetry module checks `swarm_config` for a `telemetry_installation_id` key:

1. If found, it reuses the existing ID for consistent tracking across restarts.
2. If not found, it generates a new random ID (`install_` + 16 hex characters) and persists it.
3. If config access fails (e.g. worker without DB access), an ephemeral ID (`ephemeral_` prefix) is generated for that session only.

Workers access the installation ID via HTTP (respecting the DB boundary invariant), while the API server reads it directly from the database.

The API server also stores the organization ID as `telemetry_org_id` (and the admin's email domain as `telemetry_org_domain`) next to the installation ID. Workers read both through the same HTTP config call, so events from workers and from the server carry the same organization.

A `telemetry_installed_at` timestamp is minted alongside the installation ID, but only when this process genuinely mints a **new** installation ID — it anchors "when this install came into being" independent of server restarts. An existing installation ID with no stored anchor (an install that predates this field) leaves it unset, and the field is omitted from events rather than back-filled with the current time; use `min(occurred_at)` per `installation_id` in ClickHouse as the real anchor for that population.

## How to opt out

Set the `ANONYMIZED_TELEMETRY` environment variable to `false`:

```bash title=".env"
ANONYMIZED_TELEMETRY=false
```

For Docker workers, also add it to `.env.docker`:

```bash title=".env.docker"
ANONYMIZED_TELEMETRY=false
```

You can also set it in the dashboard under Settings → Configuration → Telemetry & observability. A value stored there takes precedence over the deployment environment.

When disabled:
- No events are sent
- No installation ID is generated or stored
- The telemetry module initializes as a no-op
- The dashboard stops sending notification events. `GET /status` reports the effective state as `telemetry.enabled`, which the dashboard reads. A server that predates that field is treated as enabled.

## Technical details

- **Endpoint**: `POST https://proxy.desplega.sh/v1/events`
- **Timeout**: 5 seconds per request
- **Failure mode**: Fire-and-forget — telemetry never throws exceptions or blocks operations
- **Module**: `src/telemetry.ts` (importable from both API server and workers)
