**Sleep better without relying on a single provider.**

Open Oncall is an open source on-call workflow for Agent Swarm. A PagerDuty incident fires (or Datadog, Grafana, Opsgenie, Sentry, SigNoz, any webhook). The swarm opens a Slack thread, investigates the code, git history and telemetry, posts the root cause with a one-click approval link, and opens the fix PR once a person approves. If the provider running a step fails, the same step re-runs on the next harness: Claude, then Codex, then OpenCode.

## Prerequisites

- **Agent Swarm with a Lead** and the [Slack integration](/docs/integrations/slack) connected. The bot must be a member of your on-call channel.
- **Two or more providers.** At least two online workers on different harnesses among `claude`, `codex` and `opencode`. One worker per harness is enough. Failover needs a second harness to fail over to.
- **A repo** the workers can clone and open PRs on, with the [GitHub integration](/docs/integrations/github) set up.
- **An alert source.** PagerDuty (v3 webhooks), or anything that can POST JSON: Alertmanager, Grafana, SigNoz, Datadog, Opsgenie, Sentry. To let investigators read traces and logs, connect your observability MCP (for example SigNoz) to the workers. Without it they work from code, git history and CI.

## Install

Run these as your Lead. The Lead must create the workflow: its Slack posts go through `slack-post`, which only a lead may call.

```bash
export SWARM_URL=https://api.example.com   # your agent-swarm API
export API_KEY=...                         # swarm API key
export LEAD_ID=...                         # your Lead's agent id
H=(-H "Authorization: Bearer $API_KEY" -H "X-Agent-ID: $LEAD_ID" -H "Content-Type: application/json")
DOCS=https://docs.agent-swarm.dev/playbooks/open-oncall
```

**1. The script and the webhook secret.**

```bash
curl -s $DOCS/open-oncall.script.ts \
  | jq -Rs '{name: "open-oncall", scope: "global", source: ., description: "Open Oncall steps"}' \
  | curl -s "${H[@]}" -X POST $SWARM_URL/api/scripts/upsert --data-binary @-

export ONCALL_TOKEN=$(openssl rand -hex 24)
curl -s "${H[@]}" -X PUT $SWARM_URL/api/config \
  -d "{\"scope\":\"global\",\"key\":\"OPEN_ONCALL_WEBHOOK_TOKEN\",\"value\":\"$ONCALL_TOKEN\",\"isSecret\":true}"
```

**2. The failover block.**

```bash
FAILOVER_ID=$(curl -s $DOCS/open-oncall-failover.workflow.json \
  | curl -s "${H[@]}" -X POST $SWARM_URL/api/workflows --data-binary @- | jq -r .id)
```

**3. The workflow.** Fill your channel, repo, PagerDuty service name and approver. `GET /api/users` lists user ids.

```bash
CHANNEL=C0123456789                 # Slack channel id for alerts
REPO=acme/checkout                  # the repo Open Oncall may fix
SERVICE=checkout-api                # PagerDuty service name that maps to REPO
DASHBOARD=https://app.agent-swarm.dev  # where approvers open "Review & respond"
APPROVER=$(curl -s "${H[@]}" $SWARM_URL/api/users | jq -r '.users[] | select(.email=="you@example.com") | .id')

WORKFLOW_ID=$(curl -s $DOCS/open-oncall.workflow.json \
  | sed -e "s|<FAILOVER_WORKFLOW_ID>|$FAILOVER_ID|g" -e "s|<SLACK_CHANNEL_ID>|$CHANNEL|g" \
        -e "s|<OWNER>/<REPO>|$REPO|g" -e "s|<PAGERDUTY_SERVICE>|$SERVICE|g" \
        -e "s|<DASHBOARD_URL>|$DASHBOARD|g" -e "s|<APPROVER_USER_ID>|$APPROVER|g" \
  | curl -s "${H[@]}" -X POST $SWARM_URL/api/workflows --data-binary @- | jq -r .id)
echo "Webhook URL: $SWARM_URL/api/webhooks/$WORKFLOW_ID"
```

`SERVICE_REPOS` takes several pairs (`svc-a=org/a,svc-b=org/b`). Only repos in `ALLOWED_REPOS` are ever touched.

**4. Point PagerDuty at it.** In PagerDuty, add a Generic Webhook (v3) subscription for `incident.triggered` with the webhook URL above and a custom header `X-Open-Oncall-Token` set to `$ONCALL_TOKEN`. Other event types stop at `gate`. Any other source uses the same URL and header.

**5. Fire a test alert.**

```bash
curl -s -X POST $SWARM_URL/api/webhooks/$WORKFLOW_ID \
  -H "Content-Type: application/json" -H "X-Open-Oncall-Token: $ONCALL_TOKEN" \
  --data "$(curl -s $DOCS/pagerduty-incident-triggered.sample.json | jq --arg s "$SERVICE" '.event.data.service.summary = $s')"
```

The sample payload names the `checkout-api` service; the `jq` call swaps in yours. The intake script also accepts Alertmanager or Grafana (`status`, `alerts[]`), Datadog (`title`, `body`, `alert_transition`), Opsgenie (`action: Create`), Sentry (`data.issue` or `data.event`) and plain JSON `{alertText, service?, repo?}`.

## The Slack approval flow

The bot posts the alert as the thread root, then "Investigating" with the planned provider chain. When the investigator finishes, it posts the root cause, the evidence, the proposed fix and a **Review & respond** link. One click opens the approval request in the dashboard.

- **Approve**: the fix step opens one PR on the repo. Nothing is merged.
- **Reject**, or no answer within 6 hours: the incident is handed to a human.
- Only people listed in `approvers` can answer. Agents get a 403.

The last message in the thread is the outcome: the PR, time to root cause, time to PR, and which provider handled each step.

![Slack thread for a PagerDuty incident: alert, investigating message with the provider chain, then the root cause, evidence, proposed fix and the approval link](/playbooks/open-oncall/slack-pagerduty-thread.png)

Alerts can also come from Slack itself: a human message in a channel listed in `ALERT_CHANNELS` that matches `ALERT_PATTERN` starts a run. Bot messages never do, so point alerting tools at the webhook instead.

## Provider failover

The engine's node `retry` re-runs the same agent, so the reroute lives in the workflow:

1. `intake` reads the live agent registry and plans a chain per step: one online worker per harness, in `PROVIDER_ORDER` (`claude,codex,opencode`), best capability match first.
2. The failover block runs the step on the first worker. A failed attempt turns into a `[FAILED: reason]` output instead of failing the run.
3. A `property-match` sees `[FAILED:` and sends the same prompt to the worker on the next harness, up to three attempts.
4. `pick` returns the first success and one provider record per attempt: harness, agent, model, status, reason, and whether it looked like a provider error.
5. `close` writes those records to the run output (`providers.investigate`, `providers.fix`) and to the last Slack message.

### Drill it with `simulateProviderDown`

Add `simulateProviderDown` to any trigger. The attempt on that harness fails on purpose, as a real task, and the step moves to the next provider.

```bash
curl -s "${H[@]}" -X POST $SWARM_URL/api/workflows/$WORKFLOW_ID/trigger \
  -d "{\"channelId\":\"$CHANNEL\",\"repo\":\"$REPO\",\"simulateProviderDown\":\"claude\",
       \"alertText\":\"[FIRING] $SERVICE: POST /checkout 5xx rate 41% over 5m. Failover drill.\"}"
```

The thread marks the run as a drill, and the outcome names the reroute: `investigate → codex, failed over from claude simulated outage`.

![Slack thread for a failover drill: claude marked down, codex investigated and fixed, PR opened, incident resolved](/playbooks/open-oncall/slack-failover-drill.png)

## The app

The Open Oncall app reads the workflow's runs and shows:

- **Incidents**: status (investigating, awaiting approval, fixing, resolved, handed to a human), severity, failover, time to root cause and age.
- **Pending approvals**: Approve and Reject answer the same request the Slack thread links to, so one answer resolves both.
- **Incident detail**: the timeline from alert to resolution, with the provider, agent and model of every step. Failed attempts show as `FAILOVER`.

![Open Oncall app: stats, pending approvals with Approve and Reject, and the incidents list](/playbooks/open-oncall/app-incidents.png)

![Incident awaiting approval: claude failed, codex took over and found the root cause](/playbooks/open-oncall/app-approval-failover.png)

To install it, save the sync script, create the app with its id, and refresh it every 2 minutes with the seeded `app-sync-run` script:

```bash
curl -s $DOCS/open-oncall-app-sync.script.ts \
  | sed -e "s|<OPEN_ONCALL_WORKFLOW_ID>|$WORKFLOW_ID|" -e "s|<DASHBOARD_URL>|$DASHBOARD|" \
  | jq -Rs '{name: "open-oncall-app-sync", scope: "agent", source: .}' \
  | curl -s "${H[@]}" -X POST $SWARM_URL/api/scripts/upsert --data-binary @-
SYNC_ID=$(curl -s "${H[@]}" "$SWARM_URL/api/scripts?scope=agent" \
  | jq -r '.scripts[] | select(.name=="open-oncall-app-sync") | .id')

APP_ID=$(curl -s $DOCS/open-oncall.app.json | sed "s|<SYNC_SCRIPT_ID>|$SYNC_ID|g" \
  | curl -s "${H[@]}" -X POST $SWARM_URL/api/apps --data-binary @- | jq -r .app.id)

curl -s "${H[@]}" -X POST $SWARM_URL/api/schedules -d "{\"name\":\"open-oncall-app-sync\",
  \"targetType\":\"script\",\"scriptName\":\"app-sync-run\",\"scriptArgs\":{\"appId\":\"$APP_ID\"},\"intervalMs\":120000}"
```

![Incident detail: provider failover banner, the timeline with the provider of each step, and the root cause card](/playbooks/open-oncall/app-resolved-timeline.png)

The app is built with the [Apps](/docs/apps) feature. Ask your Lead to restyle it or add views with the `apps` skill.

## Limits

- **Approval is a link, not Slack buttons.** "Review & respond" opens the dashboard; the app's Approve and Reject buttons answer the same request.
- **PagerDuty signatures.** The trigger checks the `X-Open-Oncall-Token` header, not PagerDuty's `X-PagerDuty-Signature`.
- **Failover fires on any failed attempt**, not only provider errors. Each provider record says which kind it was.
- **A fully offline harness does not fail its task.** If a worker never claims the task, failover does not fire. There is no per-step timeout yet.
- **Every human message in an alert channel starts a run** that stops at `gate`. Filter runs on `intake.result.accept = true`.
