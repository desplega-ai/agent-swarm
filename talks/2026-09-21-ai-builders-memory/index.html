problem → solution · june 2026

On day 76, the swarm forgot.

Where we started: embed all, top-k.

  • Stale facts never die
  • Noise outranks truth
  • One bad memory reaches every agent

A half-life and a reputation.

  • Rank: match × time × use × source × reputation
  • Store pointers, not payloads
  • Learn: agents grade memories
  • Story hook (say it, do not explain it): "In June the swarm stopped finding a memory it relied on. The memory was 76 days old. The embedding was fine. The match was fine. It ranked below yesterday's chatter." The why comes on slide 7.
  • The history in one breath: we started with embed all, top-k, so stale facts never died. We added one flat 14-day half-life. Then old truth died too. That is day 76.
  • Agents are stateless workers in containers. Every session starts with amnesia. The model forgets everything between tasks.
  • Learning 1, company-first: a local CLAUDE.md teaches one laptop. A shared memory teaches every agent in the company. Benefit: lessons compound. Cost: one bad memory reaches everyone.
  • Naive RAG as memory is shared mutable global state with embeddings on top.
  • Spoken line for the right card: "a memory that evolves like a brain". It fades, it strengthens with use, it earns trust.
  • The arc: one incident, three fixes (time, pointers, reputation), and one failure we have not fixed: evals.

  • Stack, say it aloud: Bun, TypeScript, SQLite with sqlite-vec and FTS5, MCP tools.
  • WRITE: agents call memory-store, hooks write on task done and session end, files get indexed. Chunk, dedup, TTL by source, embed with text-embedding-3-small at 512 dims.
  • READ: hybrid search means semantic (sqlite-vec) plus keyword/pattern (FTS5, BM25), fused with RRF. Then 1-hop graph expansion, then the rerank formula. The prompt gets 300-char stubs plus ids.
  • * Why 1 hop: every hop multiplies the candidates and the damping compounds (0.7, then 0.49). Two hops add mostly noise. We also cap it at 5 new candidates per search, and the neighbour still has to win the same rerank. Links are outgoing only.
  • "intent + automatic": agents store on purpose (memory-store), hooks store on task done, session end, and file writes. "automatic + manual": memory is injected at task start, and agents can search mid-task.
  • LEARN: we log what we showed, three raters score it, applyRating moves alpha and beta on the same row.
  • The API server is the only owner of the database. Workers are stateless and talk HTTP. Memory survives any container.
  • Two scopes: agent (private) and swarm (shared). No vector database, no queue, no extra service.
challenge 1 · it forgot

One score does both.

score = sim(q, m) · 2−age / τsource · boostaccess · trustsource · U(α, β)

q query · m memory · sim = similarity: semantic + keyword · τ half-life of the source
trust = 1.5× stored on purpose … 0.5× session summary · α, β times it helped / did not

  • Story: "Back to day 76. This is the score. One term killed that memory." Point at time.
  • sim is not raw cosine. In hybrid mode it is the fused rank score of two searches: semantic (vectors) and keyword (FTS5), fused with RRF, k = 60. A memory found by both arms gets both contributions. Raw cosine is kept on the side.
  • trust (source_quality in the code): how much we trust where the memory came from. Stored on purpose (memory-store tool) 1.5x, indexed file 1.0x, task learning 0.7x, session summary 0.5x.
  • Everyone draws two boxes: short-term and long-term. We have one table and one reranker.
  • Short or long is not where a memory is stored. It is how fast its weight falls.
  • Factors: time = 2^(-age / half-life of the source). Use = access boost, up to 1.5x. Source = curated 1.5x down to session summary 0.5x. Reputation = usefulness from ratings, 1x to 2x.
  • Real code: src/be/memory/reranker.ts, about 100 lines. Pure function, takes "now" as an argument.
challenge 1 · why it forgot

Four sources, four half-lives.

  • Story: The reveal. The red line is the memory from slide 3. Flat 14-day half-life: 2^(-76/14) = 0.02. The fix is the four curves.
  • Each source forgets at its own speed: session summary 7d, task learning 14d, indexed file 180d, stored on purpose never.
  • The bug story (red line, day 76): the decay used to be flat 14 days for everything. A canonical memory, 76 days old, stopped showing. Embedding fine, similarity fine. 2^(-76/14) = 0.02, so the truth ranked below yesterday's chatter.
  • Fix (PR #696): half-life depends on the source. Same memory now scores x0.75 as a file, x1.0 if curated.
  • Lesson: the bug was not semantic. Most memory bugs are ranking bugs.
challenge 1 · the mental model

Short-term ↔ long-term is a dial.

  • Learning 2 numbers (prod, since 2026-05-19): 12,902 scripts written by the swarm, 128,806 script runs, 82% completed. This shows adoption. It is not a measured performance gain, so do not claim one.
  • Mention the bug here in one line if you skipped it on the chart: one decay speed for everything means the dial is stuck at one position.
  • The ends are not ours: context window on the left, model weights on the right. Memory is everything in between.
  • Names on the dial are the code names, same as the decay chart. manual = stored on purpose through the memory-store tool, mostly by agents.
  • Optional spoken line (dropped from the slide): a memory is a point in 512 dims of similarity plus 4 more axes: age, use, source, reputation.
  • Math footnote for the curious: the score is a product, so log(score) is a sum. Each factor is an independent axis next to the embedding.
  • Use moves a memory to the right: access boost and good ratings fight the decay. That is how a task learning becomes long-term.
  • Honest limit: the dial covers facts and lessons. Procedures are different. A runbook at 0.87 similarity can be 0% executable, so skills get exact, named invocation, never similarity.
  • Learning 2, own scripts: that procedural end is where the swarm writes its own scripts. Working code is saved as a typed, versioned script and called by name next time. Numbers are in the bullet above.
challenge 2 · it survives. what should it hold?

You do not remember the spreadsheet.
You remember where it lives.

  • Story: Bridge, not an incident: "Now old truth survives for 180 days or for ever. A copied payload goes stale in that time. A pointer does not." Do not claim a hoarding incident. We have none on record.
  • The contrast, say it aloud: the obvious approach is to ingest everything (copy Notion, GitHub, Slack into the vector store). Result: stale copies, sync issues, huge index, lost permissions.
  • Our take: a memory is a lesson plus pointers. It points at sources (GitHub, runbooks, Notion) and at other memories. Tools fetch the fresh data at read time.
  • Prod numbers (2026-09-21): 2,709 PR links, 1,146 wikilinks, 1,066 rated source edges. In the retrieval log, about 1 in 5 rows (27,847 of 127,530) arrived through a link, not through search.
  • A graph built by regex, not by a librarian: 0 LLM calls to build it.
  • "Lost permissions": the copy drops the access rules of the source. What only finance could read in Notion, any agent can now retrieve from the vector store.
  • Same idea in the prompt: we inject a 300-char stub plus an id. The agent calls memory-get only if it needs the rest.
  • Humans do not ingest all data. I know the GTM data is in those Notion pages, and I have the tools to read it.
  • Memory stores the lesson and the address. Tools (MCP) fetch the fresh data at read time.
  • Edges: memory → external source, free-form ids (github:, linear:, slack:, customer:). No enum, no parser. New integration costs zero code.
  • Honest status: edges carry their own rating, but they do not drive ranking yet. That is v2.
  • Optional story: an agent audited the same stale repo in 15 sessions. Every memory was accurate, none said what to do. One line ("always git fetch first") stopped it. Store the handler, not the stack trace.
  • Three things relations buy you. Reach: they find what similarity misses. Cost: 0 LLM calls to build. Order: path-like keys, S3 style, organise memories automatically.
  • Two ways in. Manual: an agent calls memory-search mid-task. Automatic: every task start runs the task text as the query. Both hit the same memory and the same graph.
  • Reach: the neighbour never matched the query. It surfaces because a strong hit links to it. It inherits the parent's score times link strength times 0.7. One hop, max 5 new candidates, then the same formula.
  • Cost: parsers find [[wikilinks]], PR refs, file paths. Deterministic link types: wikilink, sequel, PR, agent-fs file, page, external source. The trade: we only get the relations someone wrote down. No inferred links, no contradiction edges yet.
  • Order: every memory has a path-like key. Files written under /workspace/shared/memory/ or /workspace/personal/memory/ are indexed automatically and the path is the key. Other memories get scope/source/id. So memories file themselves, and you can browse by prefix like an S3 bucket.
  • The librarian approach (gbrain, dreaming): an agent files, links, and consolidates. It works, and you pay for it in AI tasks every night. We run one such job too (the daily compounding reflection), but the graph itself needs none.
  • Honest status: memory-to-memory links drive retrieval today. Rated edges to external sources are recorded, but do not drive ranking yet.
challenge 3 · it trusted every memory equally

Every memory earns a reputation.

α counts the times it helped.
β counts the times it did not.

Beta(α, β) = our belief about how often it helps.

Implicit citationcited +0.5 · ignored −0.25
LLM judgerides on the summary call
Self-ratingmemory_rate(id, useful)
f(x; α, β) = xα−1(1 − x)β−1B(α, β) mean = αα + β
  • Trap: raters shipped 2026-05-06, the day-76 fix 2026-06-08. The chapters follow ideas, not dates. Do not say "then we added ratings".
  • Story: "Day 76 taught us one more thing: every memory had the same trust. Nothing told the ranker which ones were worth it."
  • Prod numbers (2026-09-21, since May): 227K rating events. Implicit citation 166,588 (37% cited, 63% ignored). LLM judge 56,711 (60% positive). Self-rating 3,987. 3,982 of 15,660 memories have moved off Beta(1,1).
  • The formula, if someone asks: the Beta density over x, the unknown "how often does this memory help". B(α, β) only normalises it. We never compute the curve in prod, we only need the mean, α / (α + β).
  • Problem: retrieval tells you what is similar. Nothing tells you what helped.
  • Explain Beta in one breath: two counters per memory. The curve is wide when we know little, and narrow when we have evidence. A fresh memory is Beta(1,1): flat, no opinion.
  • usefulness = clamp(2α / (α + β), floor, 2.0). Fresh = exactly 1.0, a no-op. Proven climbs to 2x.
  • Three raters, one chokepoint (applyRating). Costs: citation is free, the LLM judge rides on a call we already make, self-rating is one tool call.
  • Anti-cheat: workers cannot send the server-side signal over HTTP. Self-rating is once per task per memory.
  • Default floor is 1.0: we promote proven memories, we do not yet demote bad ones.

  • Story: The twist: agents grade their own memories 90% useful. Citations say 37%. The fix has its own failure. It sets up evals.
  • Reward hacking, with data: when agents rate their own memories, 90% of ratings are "useful" (3,606 of 3,987). The server-side citation signal says only 37% of retrieved memories get used. That gap is why self-rating cannot be the only reward.
  • First row is the part we do not control: the model weights belong to the lab. Everything below it is ours.
  • Read the table top down: we act (pick memories), we get a reward (ratings), we update the value (alpha, beta). The next task ranks with the new values. That is the loop.
  • The policy is the frozen LLM plus whatever we put in its context. No gradients, no weights. The learnable parameters are two floats per memory in SQLite.
  • It is a Beta-Bernoulli bandit with one arm per memory. Same family as RLHF reward models and click feedback in recommender systems.
  • Exploration: we rank by the posterior mean only. Thompson sampling and UCB are parked, "too probabilistic" for prod. A new memory never gets a lucky chance.
  • Credit assignment: the task passed. Which memory earned it? Reward hacking is real too: an agent that rates its own memories grades its own homework. That is why the implicit signal is server-side.
landscape · where is the intelligence?

Two axes: when it thinks, what it adapts to.

  • Two questions: when does the system think (write vs read), and what does its ranking adapt to (nothing, time, usage).
  • Supermemory, gbrain, Zep, Mem0: extraction, graphs, nightly "dream" consolidation. Strong at write time.
  • The cost nobody puts on the slide: write-time intelligence means AI tasks that run to organise memory (librarian, dreaming, extraction), paid per write or per night. Read-time ranking is a few multiplications. Our raters ride on a call we already make.
  • The fair counterpoint: a librarian finds relations and contradictions that nobody wrote down. Our graph does not.
  • OpenClaw: markdown is the source of truth, with a sqlite-vec + FTS5 index and age decay on top. It is not only grep.
  • We found no system that feeds usage or ratings back into ranking. Say "we found none", not "nobody does".
  • We are not purely read-time. The daily compounding reflection runs every night: the lead agent reads the day's completed and failed tasks and folds the lessons into memory, agent identity files, and skills. It learns from usage, and it costs one AI task per night, not one per write.
  • Honest gap: that job adds lessons, it does not clean up. No contradiction handling and no consolidation of old memories yet. That is what the dreaming work is for.
challenge 4 · would we catch the next day 76?

The part we have not solved: evals.

Memory is a new hire. How do you run its performance review?

Why it is hard.

  • Time: no replay of 3 months
  • Chaos: one memory, new trajectory
  • Counterfactual: pass without it?
  • Drift: true today, false tomorrow

What we do today.

  • Unit: tests own the clock
  • Scenario: 7 facts vs near-miss lies
  • Prod: citation rate by source
  • Humans: daily use is the vibe check
  • Story: Callback: "A static eval passes on day 1 and on day 76. Match was fine. Only time changed." Trap: do not say how day 76 was found unless you remember it. I have no record of who noticed.
  • The onboarding analogy: swarm memory is like onboarding a person. It makes mistakes at first, you give it feedback, it learns. So how do you know if a person performs? Not with unit tests. With performance reviews, impact over time, and what colleagues say. Our evals look the same: ratings are the feedback, citation rate is the impact, daily human use is the peer review.
  • The unit level is solved: the reranker is pure, rerank(candidates, now). Inject the clock, assert the ranking.
  • The scenario level is OK: seed memories, tempt the model with plausible wrong defaults, grade facts deterministically. A judge only checks that the agent searched and did not guess.
  • Humans as evaluators: people use the swarm every day and complain fast when it forgets or repeats a mistake. It is a vibe check, not a metric, and today it is our most sensitive signal.
  • The system level is open: does memory make the swarm better over a month? We only have trends from production, no controlled experiment.
