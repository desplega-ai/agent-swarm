  • Say (45s): "One SQLite file. Agents and hooks write. Every task reads: hybrid search, one hop in a graph, then one score. And we log what we showed, so the next score knows what helped."
  • Stack: Bun, TypeScript, SQLite with sqlite-vec and FTS5, MCP tools. No vector database, no queue, no extra service.
  • WRITE: agents call memory-store, hooks write on task done and session end, files get indexed. Embed with text-embedding-3-small at 512 dims.
  • READ: semantic (sqlite-vec) plus keyword (FTS5, BM25), fused with RRF. Then 1-hop graph expansion, then the rerank formula. The prompt gets 300-char stubs plus ids.
  • LEARN: three raters score what we showed. applyRating moves alpha and beta on the same row.
  • Two scopes: agent (private) and swarm (shared).
  • New since September (checked in code 2026-11-24):
  • Write gate: a task can leave a one-line learning. A noise floor rejects text that holds no lesson, and a near-duplicate of a swarm memory is not stored. Learnings expire after 30 days.
  • A curated tree under /longterm (facts, decisions, entities). A memory there never decays, whatever its source. Dreaming maintains it.
  • Read gate: all retrieval arms are on one 0 to 1 scale, and a memory is injected only if it is relevant enough.
  • Raters are on by default now (citation + self). The LLM judge is opt-in.
  • Demotion exists now: a memory rated wrong can fall to 0.5x. See slide 7.
  • Search runs in worker threads. Postgres is a second storage engine since 2026-11-23. The default is still one SQLite file.

  • Say (40s): "Back to day 76. This is the score. Five factors, one product. One term killed that memory." Point at time.

part 1 · memory · what deserves to stay

Every memory earns a reputation

α counts the times it helped.
β counts the times it did not.

Beta(α, β): a distribution on 0 to 1.
Our belief about how often it helps.

Implicit citationcited: α +0.5 · ignored: β +0.25
LLM judgerides on the summary call
Self-ratingmemory_rate(id, useful)
f(x; α, β) = xα−1(1 − x)β−1B(α, β) mean = αα + β

x = how often it helps, from 0 to 1 · fresh memory: Beta(1, 1), mean 0.5

  • Say (50s): "Time tells you what is old. It does not tell you what helped. So every memory has two counters. Three raters move them. We cannot train the model. We can train what it remembers."
  • The twist, one line: "Ask the agents: 90% of their memories are useful. Watch the agents: 37% get cited. So the reward that counts is one the agent cannot write."
  • Prod numbers (2026-09-21, since May): 227K rating events. Implicit citation 166,588 (37% cited). LLM judge 56,711 (60% positive). Self-rating 3,987 (90% "useful"). These are September numbers. Say "in September".
  • The formulas, if someone asks:
  • Yes, Beta is a probability distribution, and it lives on 0 to 1 only. x is the unknown we care about: the chance that this memory helps when we show it. The curve says how much we believe each value of x.
  • Left formula: the density. α − 1 and β − 1 are the exponents, so more "helped" pushes the mass to the right and more "did not" pushes it to the left. B(α, β) is a constant that makes the area equal to 1. We never compute it.
  • Right formula: the mean. It is all we use in production: α / (α + β). Beta(1, 1) gives 0.5. Beta(6, 2) gives 0.75. Beta(2, 5) gives 0.29. These are the three curves on the chart.
  • Why Beta and not a plain average: with 1 good rating out of 1, an average says 100%. Beta(2, 1) says 67%, and the curve is still wide. It does not trust small samples.
  • How a rating moves it: cited adds 0.5 to α, ignored adds 0.25 to β. The other raters add their own weights the same way.
  • Beta in one breath: the curve is wide when we know little, and narrow when we have evidence. A fresh memory is Beta(1,1): flat, no opinion.
  • usefulness = clamp(2α / (α + β), floor, 2.0). Proven memories climb to 2x. New since November: a memory can fall to 0.5x, but only with evidence that it was rated wrong. "Shown and not used" does not demote.
  • The RL mapping is in the appendix (slide 22) if someone asks.

  • Five lanes: profile files (identity and instructions), memory, skills, scripts, and the lead's heartbeat checklist.
  • Say it aloud, there is no legend: "Amber means a model runs. All the rest is code."

part 3 · both · the open problem

Changed is not improved

Why it is hard

  • No replay: a day of tasks happens once
  • Shorter is not better
  • Counterfactual: the same day, no change
  • Drift: true today, false tomorrow

What we watch: second-order evals

  • Repeated work: schedules, PRs, reviews
  • A skill changes: same PR merge rate?
  • A script ships: does its use go up?
  • Last night: 8 of 9 changes survived
  • Say (70s): "Here is the part we have not solved. The swarm changes itself every night. How do you know that it improved, and not only changed? You cannot replay yesterday. A shorter prompt is not a better prompt. What we watch today is second-order evals. We do not grade the change. We watch the work that uses it. And a swarm repeats itself a lot: the same schedules, the same PR flow, the same reviews, every day. So if dreaming changes a skill that mostly the coder uses, and the share of merged PRs stays the same, the change is fine. If it drops, we see it the next day. If a new script ships and agents start to use it, that is adoption. Repetition is our benchmark."
  • The nightly numbers: did last night's change survive, or did someone revert it? 8 of 9 last night. Did a cut come back because an agent missed it? 0 of 54 so far. Size and cost, night over night. And every new script ships with two controls: one run that must pass and one that must fail.
  • Trap: the second-order reading is mostly done by people and by the lead today, on top of the per-agent stats that the gather step collects. I did not find an automated gate that compares a PR merge rate before and after a skill change. Say "we watch", not "the system checks".
  • Be honest: these measure stability and cost. They do not measure quality. "It survived" is not "it is better".
  • The same problem on the memory side: a static eval passes on day 1 and on day 76. The match was fine, only time changed. There we have unit tests that own the clock, scenario evals with near-miss lies, and the citation rate by source in production.
  • The direction: replay. Record real tasks, then run them again against today's agent with a cheap model, before the change ships. The blog post calls this "dry evolution". Trap: I could not confirm that a replay runs in the nightly workflow today. Present it as the direction, not as a feature.
  • Numbers on the slide are from last night's report: survival 8 of 9, cuts scored 54, reverted 0, reintroduced 0.

  • It is a Beta-Bernoulli bandit with one arm per memory. No gradients, no weights. The learnable parameters are two floats per memory in SQLite.
  • Exploration: we rank by the mean of the Beta only. A new memory starts neutral at 1.0, a proven one can reach 2.0. So old winners keep winning. Thompson sampling and UCB are the known fixes. We parked them: random retrieval in prod makes runs hard to reproduce.
  • Credit assignment: a task retrieves 5 to 10 memories and then passes or fails. One bit for the whole task. We reward each memory with proxies: was it cited, did the judge say it helped. We know what got USED, not what CAUSED the pass.
  • Cited, not rated. 37% is measured by the server: the id of the memory shows up later in the session log of the task. Nobody rates anything for that number. The 90% is the rated one.
  • The two numbers measure different things. 90%: agents chose to rate 3,987 memories and 3,606 say "useful". 37%: the server checked all 166,588 retrievals for a later citation. The 90% has a selection bias. The 37% is a floor. Numbers are from September.
